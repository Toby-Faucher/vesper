# 0008. A strict Content-Security-Policy sent by the server

Status: accepted, 2026-11-01. Supersedes [0004](0004-no-csp-yet.md).

Context: [0004](0004-no-csp-yet.md) shipped without a CSP until the app showed user text. It now shows chat messages, Markdown,
uploaded images and search snippets. The script set is settled: the Vite bundle, the AudioWorklet module, the DSP module
worker and the denoiser WASM under `/dsp/`.

Decision: the server sets the policy in `guard` (`crates/vesper-server/src/lib.rs`, `csp()`) on every response, so it does not
depend on the proxy. The WebSocket origin is built from `VESPER_ORIGIN` (`ws://` or `wss://`):

```
default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self'; connect-src 'self' wss://<host>;
img-src 'self' blob:; media-src 'self' blob:; style-src 'self' 'unsafe-inline'; object-src 'none'; base-uri 'none';
frame-ancestors 'none'; form-action 'self'
```

- A response that already has a CSP keeps it. Only `/api/uploads/*` sets one (`default-src 'none'; sandbox`), so an uploaded file
  never runs under the page's policy.
- Also on every response: `Referrer-Policy: no-referrer`, `Permissions-Policy: microphone=(self), camera=(), geolocation=()`,
  `Cross-Origin-Opener-Policy: same-origin`, `X-Content-Type-Options: nosniff`, and `Strict-Transport-Security: max-age=31536000`
  when `VESPER_ORIGIN` is https (never on plain http, which would pin a name to https).

Why each relaxation is there, and how it was checked:

- `'wasm-unsafe-eval'`: measured. With it removed from the DSP worker's response, Chromium refuses
  `WebAssembly.instantiateStreaming` and the app falls back to browser suppression ("denoiser error: ... 'unsafe-eval' is not an
  allowed source of script"). It allows compiling WASM only, not JavaScript `eval`. The page's own response was not measured
  apart from the worker's: one policy is sent everywhere.
- `'unsafe-inline'` for styles only: Svelte writes `style` attributes. Scripts have no `'unsafe-inline'` and no `'unsafe-eval'`.
- `blob:` in `img-src` and `media-src`: local previews. No `blob:` or `data:` in `script-src` or `worker-src`: the worklet and the
  worker are files under `/assets/` (checked in `web/dist`: no `data:` URLs, so `build.assetsInlineLimit` needs no change).
- `connect-src` names the WebSocket origin as well as `'self'`, because some older browsers do not match `ws:` with `'self'`.

Verified: `crates/vesper-server/tests/static_files.rs` (`csp_on_html_and_api`, `https_origin_adds_hsts_and_wss`) and
`tests/uploads.rs` (`upload_keeps_sandbox_csp`). `npm --prefix web run e2e` records `securitypolicyviolation` events and CSP
console errors in both browsers through sign up, sign in, voice, chat, upload and search, and fails on any. With `dist/dsp/` built,
`flows.mjs` also starts the DeepFilterNet worklet, worker and WASM under the policy. Chromium only; Firefox and Safari not tried.

Consequences: a new script source, worker, frame or connect target needs a change here and in `csp()`. A CSP block inside the DSP
worker does not reach the page console: it shows as the fallback reason in the status line. `deploy/Caddyfile.example` no longer
sets these headers, apart from HSTS (the server sends the same value).

Addendum, 2026-11-01 (Web Push, issue #58): the push service worker `/sw.js` falls under `worker-src 'self'` and the install
manifest under `default-src 'self'` (no `manifest-src` needed), so the policy is unchanged. `static_files.rs`
(`service_worker_and_manifest`) checks both are served with the policy; `web/e2e/push.mjs` registers the worker with no violation.
